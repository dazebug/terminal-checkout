## Architecture — TCC forces this shape

```
Chrome → relay (stdio↔socket forwarding only) → unix socket → app (rendering, validation, terminal execution)
```

- macOS TCC attributes permissions to the responsible process. If a child process of Chrome runs osascript, the permission attaches to **Chrome**. So the relay must contain no execution logic; actual execution belongs to the app, which is launched via `open` (LaunchServices) and thereby becomes its own responsible process. No refactoring that breaks this separation
- The unix socket path must stay short — there is a 104-byte limit. That applies equally when tests override it via `TERMINAL_CHECKOUT_SOCKET`
- The Native Messaging host name (`com.dazebug.terminal_checkout`) and the app bundle ID (`com.dazebug.terminal-checkout`) are different namespaces — host names cannot contain hyphens, which is why the spellings diverge. Don't mix them

## Development notes

- The app is the single source of truth for terminal selection — the extension gets no way to specify a terminal. The stored value `iterm` is an identifier that denotes iTerm2 regardless of the app's product name — don't change it
- The touch points and hands-on checklist for supporting a new terminal are in `docs/new-terminal-checklist.md` — the branches are scattered across Core, the App, and the setup window, and neither the unit tests nor `app/e2e.sh` actually opens a terminal, so a missed branch surfaces only in real use. When you build a new feature (any change that adds execution paths: button kinds, pages they attach to, claude input delivery mechanisms), add items to that checklist too — paths not on the list stay unverified on the next terminal
- The app returns variable-validation failures and terminal-launch failures as a normal response `{success:false, error}`, not as an exception (`Request.handleRequest`) — if the extension doesn't check that value, a failure shows up on the button as success. Route every new command-sending path through this check. `chrome.runtime.sendMessage` does not reject on a `{success:false}` response either, so extension-internal hops need the same check
- Extension-install completion is judged by a recorded socket request, not by the folder being prepared — a prepared folder can't tell you whether Chrome actually loaded it
- Variable-value validation is a per-character whitelist. It also closes the hole where the Python-era regex's `$` allowed a single trailing newline — do not revert to a regex
- `{base}` (the branch a PR merges into), unlike `{main}`, goes through no override or default fallback. On detection failure it is simply not sent, letting the app reject — failing beats merging or rebasing onto the wrong branch
- The three gates in claude input delivery (`Core/ClaudeInjector.swift`) must not be bypassed: ① the foreground process is claude, ② the tty is in raw mode, ③ same PID as the claude that was originally prepared. Without ①, the shell receives the mistyped input, Enter included; without ②, in the canonical-mode window right after exec, kernel echo gets mistaken for claude rendering the input and the first input is lost; without ③, after the original session dies, leftover input flows into a new claude on the same tty — and if it's a `!…` shell-mode input, an unintended command even gets executed (all verified empirically). **Every site that emits bytes** (probe marker, input-box clear, body typing, CR, end-of-delivery cleanup) goes through the single function `send(_:io:)`, which re-checks ③ — checking at each site separately guarantees a missed site (body typing actually was missing once). The window between check and send remains. **`TIOCSTI` only enqueues; it doesn't decide who reads**, so app-side gates alone are insufficient — immediately before injecting, the helper also verifies "the process that will read this tty right now" via `tcgetpgrp(ttyFD) == getpgid(expected pid)`. It compares the process group rather than the pid because the claude pid the app picks is sometimes not the group leader (3 of 13 panes, verified empirically) — there was a time we assumed "we just confirmed screen reflection, so it's safe," but even between that check and the CR there is a polling-interval-sized gap, and if the session changes within it, whatever the user was typing gets submitted and executed
- claude input follows [type without newline → screen-reflection check → submit with CR (`\r`)] — LF (`\n`) is not recognized as submit (verified empirically), and even past the gates there are moments when the TUI hasn't drawn the input yet, so never send CR before confirming reflection. Do not simplify this into "send text+newline in one shot"
- Warp has no way to address a pane — no AppleScript, no pane-control CLI, `warpctrl` is disabled by default on Stable, and the AX tree exposes a single `AXTextArea` that is reused across tab switches (verified empirically). So new tabs open via a Tab Config TOML + `warp://tab_config/<stem>`, and claude input is injected by a helper launched inside that pane (`Sources/WarpHelper`) that writes directly into the tty input queue with `TIOCSTI`. All three constraints on the helper are empirical: **no `setsid`** (leaving the session means that tty is no longer the controlling terminal, so the `isctty` check blocks it), **`SIGTTOU` must be ignored** (TIOCSTI from a background process group gets EIO if orphaned, otherwise a SIGTTOU arrives and it's EINTR), **pass the tty name read from the stdio the shell handed down** (if the child opens `/dev/tty` and calls `ttyname`, it gets `/dev/tty` back, unusable for `ps -t` / `stty -f`)
- The Warp injection helper's **trust boundary is the uid** — a same-uid process can inject arbitrary input into that pane via the live helper socket, and we do not prevent that (there is nowhere to hide from the same uid: the socket path is visible in the Tab Config and on the pane screen). The only axis left to narrow is lifetime, so the helper is killed the moment delivery ends. The boundary declaration and the list of residuals that lean on it are in the preamble of `Sources/WarpHelper/main.swift` — don't mix what leans on the boundary with what remains as a race
- The screen-reflection check passes **only when the probe appears one more time than in the screen snapshot taken right before typing** (`screenReflectsNewInput`). If no snapshot could be taken, treat it as a failed check. Count comparison alone is not enough — without a guarantee that the screen is our pane, another pane receiving the same text also raises the count
- Terminals whose screen reads aren't pane-accurate (Warp) run a **pane proof** first for every input (`ClaudeSessionIO.screenNeedsPaneProof`): inject a nonce that can only enter our tty and check whether it newly appears on screen — if it does, the screen being read is our pane. The marker is cleared with Ctrl+U before the real input is typed (submitted together, claude would receive the wrong thing). The consequence is that **delivery happens only while the user is looking at that tab** — don't work around this; document it as-is. Switching to another tab and back resumes delivery to completion
- That proof is valid **only up to the moment the body is typed** (1–3 seconds between proof and CR). It cannot be re-run just before CR — by then the input box holds the body, so the marker would mix into the submission, and the append-then-erase variant has the same problem in the read that confirms "erased" (on someone else's screen the marker isn't visible either → false positive → submitting `body+marker`). The remaining damage when all three conditions coincide is **a single empty CR**: every byte up to the CR goes only to our tty (there is no synthetic-keystroke or AX-write path in the code), so there is no way someone else's pane content gets submitted
- Injection enters our tty regardless of focus — **"not confirmed on screen" does not mean "not in the input box."** So whenever delivery fails to run to completion (even with Accessibility permission intact, even if only the reflection check failed), clear the fragment of ours that may remain in the input box with Ctrl+U before finishing. The condition is not "permission lost" but "incomplete + we ever sent bytes," and since multiple branches end in failure (session check between inputs failing, retries exhausted), that cleanup lives in **one place**, `submitClaudeInputs` — put it outside and only one branch reaches the cleanup
- Don't use the "tty input queue is empty" signal (`FIONREAD`=0) in place of the reflection check — it only means `read()` happened, not that the input box drew it; claude discarded input during initialization, we sent an empty CR onto it and recorded "delivered" (verified empirically). That is why, on Warp, Accessibility permission is a hard requirement for buttons that schedule claude input (command execution doesn't need it). Queue occupancy is good for exactly two things: **backpressure** when writing in chunks, and the **negative** signal "not read yet." **Never infer whose the remaining bytes are** — `FIONREAD` is an unattributed total; it cannot separate ours from keys the user just typed. That is why the branch that compared against the previous sample, judged "didn't grow → ours," and discarded via `tcflush` was removed (the first sample had nothing to compare against so it filtered nothing, and a `10 → 9` — the user typing while claude reads — shrinks the total into the same misjudgment). The cost is a wider window in which our unread bytes linger as residue in the shell's line buffer, but **visible residue beats silent deletion**
- `extension/defaults.js` is the single source for defaults, presets, visibility rules, page classification, and storage keys — the content script, service worker, and options page all load this file first. Page classification is where divergence is most likely: an extension-icon click doesn't go through the content script, so the service worker classifies on its own; if they disagree, commands run on non-repository paths (`/settings/profile`, 404). The options-page CSS tokens mirror the app's `Theme.swift` palette — change a color on one side and change the other too
- On the options page, storage writes happen only through the single [Save] button — import doesn't write to storage either; it only fills the edit state
- Issue buttons attach to the status-badge (Open/Closed) row — placed inside the title (h1) they get pushed to the next line depending on title length, and module CSS class names carry build hashes so they can't be used as selectors (hence finding the flex ancestor wrapping the badge and appending there)
- When verifying drag reordering via browser automation, CDP synthetic input reproduces only `dragstart` through `dragend` and cannot complete a native `drop` (verified empirically) — verify post-drop logic with a synthetic `DragEvent`
- Tool checking (`Core/ToolChecker.swift`) must launch a login shell interactively (`-i`) — `z` is a shell function zoxide defines in rc files, undiscoverable by executable lookup, and a GUI app's PATH/SHELL differ from the login shell's
- GUI apps get a PATH on the order of `/usr/bin:/bin`, so the wezterm CLI must be searched at explicit candidates like `/opt/homebrew/bin`
- New tabs are created in the window the user was looking at — without `--window-id`, `wezterm cli spawn` picks the window from `WEZTERM_PANE`, which a GUI app doesn't have, so the tab lands in the mux's first (= oldest) window (verified empirically). The fallbacks for "no window found" and "the chosen window closed in the meantime" are part of the same unit (`Core/TerminalRunner.swift`) — give up midway and the `wezterm start` fallback opens a new window, resurrecting the very symptom being fixed. iTerm2's `current window` is already the most recently active window and needs no such handling
- The extension ID is pinned by the manifest `key` — the ID must be identical across machines so `storage.sync` settings sync between Chromes on the same account. The private key (`~/Library/Application Support/TerminalCheckout/extension-key.pem`) lives outside the repo; unpacked loading needs only the manifest's public key. The path-based old ID also registered in `allowed_origins` is transitional
- Reflecting extension changes requires a refresh at chrome://extensions — except that **changes that alter the ID (like adding a key) require remove-and-reload, not a refresh**
- When moving to the Chrome Web Store, add the store ID to `Installer.allowedExtensionIDs`. A CWS upload zip cannot contain the manifest `key` field — uploading a key-less zip first to reserve the store ID is the official procedure
