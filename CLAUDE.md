## Architecture — TCC forces this shape

```
Chrome → relay (stdio↔socket forwarding only) → unix socket → app (rendering, validation, terminal execution)
```

- macOS TCC attributes permissions to the responsible process. If a child process of Chrome runs osascript, the permission attaches to **Chrome**. So the relay must contain no execution logic; actual execution belongs to the app, which is launched via `open` (LaunchServices) and thereby becomes its own responsible process. No refactoring that breaks this separation
- The unix socket path must stay short — there is a 104-byte limit. That applies equally when tests override it via `TERMINAL_CHECKOUT_SOCKET`
- The Native Messaging host name (`com.dazebug.terminal_checkout`) and the app bundle ID (`com.dazebug.terminal-checkout`) are different namespaces — host names cannot contain hyphens, which is why the spellings diverge. Don't mix them

## Development notes

- The app is the single source of truth for terminal selection — the extension gets no way to specify a terminal. The stored value `iterm` is an identifier that denotes iTerm2 regardless of the app's product name — don't change it
- The parent-side `setpgid` is already too late when `Process.run()` returns (20/20 EACCES on Darwin 25.4.0); process-group cleanup is best effort, and `runProcess`'s real bound comes from closing pipe readers. Descendant processes can remain
- cmux retry classification is typed rather than substring-based — the measured forms are anchored with the CLI's **required** `Error: ` prefix at `Error: Failed to connect to socket at ` and `Error: Socket not found at `; a prefixless message fails closed, and a partial match cannot distinguish a post-create failure after the server already made a workspace.
- `runProcess` decodes output lossily so one truncated multibyte sequence does not discard a valid prefix; invalid original bytes are logged.
- The touch points and hands-on checklist for supporting a new terminal are in `docs/new-terminal-checklist.md` — the branches are scattered across Core, the App, and the setup window, and neither the unit tests nor `app/e2e.sh` actually opens a terminal, so a missed branch surfaces only in real use. When you build a new feature (any change that adds execution paths: button kinds, pages they attach to, claude input delivery mechanisms), add items to that checklist too — paths not on the list stay unverified on the next terminal
- The app returns variable-validation failures and terminal-launch failures as a normal response `{success:false, error}`, not as an exception (`Request.handleRequest`) — if the extension doesn't check that value, a failure shows up on the button as success. Route every new command-sending path through this check. `chrome.runtime.sendMessage` does not reject on a `{success:false}` response either, so extension-internal hops need the same check
- Extension-install completion is judged by a recorded socket request, not by the folder being prepared — a prepared folder can't tell you whether Chrome actually loaded it. What that record testifies is **"some extension context reached the host", and nothing more** (D26): `HostServer.serve` stamps it on every framed message *before* parsing, so a malformed frame and a rejected request count equally. The current service worker sends no request merely because Chrome loaded it, so the normal way to complete this step is to press a Terminal Checkout button once; don't read the record as evidence that the command ran
- Variable-value validation is a per-character whitelist. It also closes the hole where the Python-era regex's `$` allowed a single trailing newline — do not revert to a regex
- `{base}` (the branch a PR merges into), unlike `{main}`, goes through no override or default fallback. On detection failure it is simply not sent, letting the app reject — failing beats merging or rebasing onto the wrong branch
- The three gates in claude input delivery (`Core/ClaudeInjector.swift`) must not be bypassed: ① the foreground process is claude, ② the tty is in raw mode, ③ same PID as the claude that was originally prepared. Without ①, the shell receives the mistyped input, Enter included; without ②, in the canonical-mode window right after exec, kernel echo gets mistaken for claude rendering the input and the first input is lost; without ③, after the original session dies, leftover input flows into a new claude on the same tty — and if it's a `!…` shell-mode input, an unintended command even gets executed (all verified empirically). **Every site that emits bytes** (probe marker, input-box clear, body typing, CR, end-of-delivery cleanup) goes through the single function `send(_:io:)`, which re-checks ③ — checking at each site separately guarantees a missed site (body typing actually was missing once). The window between check and send remains. **`TIOCSTI` only enqueues; it doesn't decide who reads**, so app-side gates alone are insufficient — immediately before injecting, the helper also verifies "the process that will read this tty right now" via `tcgetpgrp(ttyFD) == getpgid(expected pid)`. It compares the process group rather than the pid because the claude pid the app picks is sometimes not the group leader (3 of 13 panes, verified empirically) — there was a time we assumed "we just confirmed screen reflection, so it's safe," but even between that check and the CR there is a polling-interval-sized gap, and if the session changes within it, whatever the user was typing gets submitted and executed
- claude input follows [type without newline → screen-reflection check → submit with CR (`\r`)] — LF (`\n`) is not recognized as submit (verified empirically), and even past the gates there are moments when the TUI hasn't drawn the input yet, so never send CR before confirming reflection. Do not simplify this into "send text+newline in one shot". Inputs containing LF or CR are rejected at the app boundary because every typed terminal carrier submits them before reflection can be confirmed
- `claude_inputs` also rejects C0 control characters and DEL at the app boundary: they are typed bytes, and reflection checks only the first 24 characters, so a control byte after that prefix could alter the command before CR without being reflected.
- **A `!` input is typed into claude's shell mode — never pre-run and pasted.** The app used to run those lines in the pane's shell and hand claude the captured output in argv; that was removed in round 10 (user decision) after measuring that `claude -- '!echo x'` does **not** enter shell mode: it arrives as an ordinary message and claude runs it with its Bash tool, which can stop for a permission prompt, is a model judgement rather than a shell fact, and spends a turn. What survives of the optimisation is cycles, not routes: **a run of consecutive `!` inputs is typed as one line joined with `;`**, each body behind a `/bin/echo '==== !… ===='` banner so the outputs can be told apart — absolute path, because an earlier body on that same line could have redefined the `echo` builtin, and no function or alias can capture a name containing `/`. The banner exists **only on the merged line**; a run that is typed input by input has none, and neither does a lone `!`. The leading `/` right after the `!` was measured, not assumed: shell mode survives it and no slash palette opens. A run merges only when every body is provably safe to join (`claudeBodyJoinsSafely`), because joining is not free: separate `!` submissions share **no** shell state (each is a fresh eval, measured), while a merged line does, so a body that runs `cd`/`export`/`source`/`exit`/an assignment would change what the commands after it do (`["!cd sub", "!rm -rf build"]` removes a different directory merged than typed apart). The other half of the gate is syntax that could reach past its own end, and there the rule is **blunt on purpose: no judgement of position at all** — any unquoted `#` or `=` folds the run wherever it sits, as do a heredoc, a trailing `&`, an unterminated quote, a compound-command keyword (`if`/`for`/`while`/`case`… — one constant, `shellCompoundCommandKeywords`, shared with the append scanner, which folded them while this gate did not), and a body whose first or last character is an operator. Two silent-loss defects came from the opposite posture, a rule that tried to prove a given `#` was literal and read `!echo one;# note` as text (measured: the merged line then prints `one` and exits 0 — the next input disappears with no error anywhere). Over-folding costs one type/submit cycle and nothing else, which is also why a merged line over `claudeMergedLineLimit` (4 KiB, the Warp helper's 8 KiB payload ceiling giving itself room) is typed input by input, never truncated. `;` and not `&&`, because separate `!` lines never stopped each other. Only **exactly one** plain-text input, with nothing else in the list, still rides in argv, and never alongside typing — submitting that message clears the input box 2∼3s after start and wipes whatever was typed meanwhile (measured)
- Of the 11 shipped presets **3 schedule claude input, and all 3 are `!`-only**, so everything they schedule is typed and on Warp those three need the Accessibility permission. The other 8 schedule none, take no input path at all and need nothing. Both overstatements have been in this file: "the presets need no permission" (true only while `!` was pre-run) and "every preset needs it" (round 13) — count the three before writing either
- **Every input is preceded by a throwaway-marker experiment, and it is not flab**: [type a random marker → see it appear → clear (Ctrl+U) → see it disappear → type the body **once** → CR]. Seeing our text appear on screen does **not** mean it is in the input box — claude draws the same string in hint lines below the box (`try /review`), so a screen that gains one of those while our typing was dropped is indistinguishable from a render, and the CR that follows submits whatever the box really holds (reproduced). **Text that disappears when the input box is cleared was in the input box** — that is the only attribution obtainable from outside, the same observation is the only evidence that the TUI *processed* our Ctrl+U (AppleScript and the wezterm CLI report that the terminal accepted the write, never that claude acted on it; do not write "the clear succeeded" anywhere), and a random marker appearing is also the proof that the screen being read is our pane — one experiment, three answers, so it replaced the separate Warp-only pane proof rather than sitting beside it
- **The experiment must never use the body text.** It briefly leaves what it typed on screen, and the user may press Enter right then — on Warp they are watching that tab by design — which submits it: with the body in the box their Enter runs the command, and the app, which can only count the CRs *it* sent, then clears, retypes and submits, so a `!` line runs **twice** (reproduced; this is why the body is typed exactly once and only after the marker experiment has passed). The related rule: after a CR has gone out — even one whose call reported failure — that input is never typed again, for the same reason. Retyping before the first CR is the only retyping that cannot duplicate a message; keep the two rules next to each other so neither gets cited as grounds for the other
- Warp has no way to address a pane — no AppleScript, no pane-control CLI, `warpctrl` is disabled by default on Stable, and the AX tree exposes a single `AXTextArea` that is reused across tab switches (verified empirically). So new tabs open via a Tab Config TOML + `warp://tab_config/<stem>`, and claude input is injected by a helper launched inside that pane (`Sources/WarpHelper`) that writes directly into the tty input queue with `TIOCSTI`. All three constraints on the helper are empirical: **no `setsid`** (leaving the session means that tty is no longer the controlling terminal, so the `isctty` check blocks it), **`SIGTTOU` must be ignored** (TIOCSTI from a background process group gets EIO if orphaned, otherwise a SIGTTOU arrives and it's EINTR), **pass the tty name read from the stdio the shell handed down** (if the child opens `/dev/tty` and calls `ttyname`, it gets `/dev/tty` back, unusable for `ps -t` / `stty -f`)
- cmux's control path is `cmux rpc` only — `cmux send`/`--command` pass through `unescapeSendText`, which changes a literal `\n` to CR but does not handle `\\`, and the server changes LF in text to CR too, so a newline in text submits early; these are cmux v0.64.22 behaviors, not interchangeable carriers
- cmux requires a socket control mode without ancestry checking; `automation` is recommended, while `password` and `allowAll` also pass (D1). Its boundary is the same macOS uid as the app socket. The setup window's live status probe uses `cmux ping`: a missing default socket means "not running" only when ping neither succeeds nor reports Access denied, because cmux discovers its socket through `CMUX_SOCKET_PATH` or `/tmp/cmux-last-socket-path`, so PONG or denial wins. The execution path has a different oracle and does not preflight ping: `workspace.create` is tried first, a socket denial fails immediately, and only another first failure permits one launch and one retry when it is proven that no server-side effect occurred — `workspace.create` is not idempotent. Never read the settings file to infer a state. Access denied cannot be fixed by launching cmux, so report it immediately or an automation-mode problem is misdiagnosed as "cmux is not running"
- This app does not write the cmux settings file: its button opens it and copies the value only. The alternative `cmux settings automation` is blocked by socket denial while automation is off (driver measurement 2026-08-27: `Error: ERROR: Access denied - only processes started inside cmux can connect`), so CLI delegation is not available.
- cmux tty names come from `debug.terminals` as basenames reported by shell integration. A `focus:false` workspace can have no pty at all, yielding tty null and `queued:true`; queued is not loss because the surface flushes after warm-up (measured), so workspace creation uses `focus:true` and the reflection check still must precede CR
- **cmux's key path is unusable under claude — every byte goes through `surface.send_text`.** claude enables the kitty keyboard protocol (flag 1, `CSI > 1 u`) and modifyOtherKeys 2, so cmux's `surface.send_key` — which runs libghostty's key encoder — turns `ctrl+u` into a CSI-u sequence that claude does not act on: measured (cmux 0.64.22, Claude Code 2.1.246), `send_key ctrl+u` left the marker in the box and `send_key backspace` deleted one character, so the marker experiment saw an 11-of-12-character remnant, called it erased, and the body was submitted glued to it (`tctqr20ckbi!echo …`). The raw-shell `cat -v` measurement that showed `^U` was made with the protocol off and does not transfer. The two-byte clear is therefore **two `send_text` calls, one byte each**: cmux turns `0x7F` (and `0x08`/`0x09`) into a key event, and a key event does not stay ordered behind text buffered in the same call — one call carrying `0x15 0x7F` cleared the text but left the `!`. And the erased check counts every 6-character window of the marker, not the whole string, so a one-character remnant fails it.
- cmux RPC parameters travel in argv because the CLI has no stdin JSON path, so non-ASCII is escaped as `\uXXXX` to keep Foundation from NFD-reencoding user text
- Launch cmux with `open -b com.cmuxterm.app` and no arguments — an argument is treated as an explicit launch and disables session restoration (cmux source v0.64.22)
- The Warp injection helper's **trust boundary is the uid** — a same-uid process can inject arbitrary input into that pane via the live helper socket, and we do not prevent that (there is nowhere to hide from the same uid: the socket path is visible in the Tab Config and on the pane screen). The only axis left to narrow is lifetime, so the helper is killed the moment delivery ends. The boundary declaration and the list of residuals that lean on it are in the preamble of `Sources/WarpHelper/main.swift` — don't mix what leans on the boundary with what remains as a race
- The screen-reflection check passes **only when the probe appears one more time than in the screen snapshot taken right before typing** (`screenReflectsNewInput`). If no snapshot could be taken, treat it as a failed check. Count comparison alone is not enough — without a guarantee that the screen is our pane, another pane receiving the same text also raises the count
- Terminals whose screen reads aren't pane-accurate (Warp) run a **pane proof** first for every input (`ClaudeSessionIO.screenNeedsPaneProof`): inject a nonce that can only enter our tty and check whether it newly appears on screen — if it does, the screen being read is our pane. The marker is cleared with Ctrl+U before the real input is typed (submitted together, claude would receive the wrong thing). The consequence is that **delivery happens only while the user is looking at that tab** — don't work around this; document it as-is. Switching to another tab and back resumes delivery to completion. cmux is the opposite grade: its `surface.read_text` is addressed by surface UUID, so it needs no pane proof and continues in a background tab
- That proof is valid **only up to the moment the body is typed** (1–3 seconds between proof and CR). It cannot be re-run just before CR — by then the input box holds the body, so the marker would mix into the submission, and the append-then-erase variant has the same problem in the read that confirms "erased" (on someone else's screen the marker isn't visible either → false positive → submitting `body+marker`). The remaining damage when all three conditions coincide is **a single empty CR**: every byte up to the CR goes only to our tty (there is no synthetic-keystroke or AX-write path in the code), so there is no way someone else's pane content gets submitted
- Injection enters our tty regardless of focus — **"not confirmed on screen" does not mean "not in the input box."** Keep the two questions apart: *did claude receive the message* is not established at all (nothing outside the TUI can), while *is the input box empty* decides where the next bytes land and whether to clean up, so it is never assumed. The box is cleared with Ctrl+U **immediately before every input** and once when delivery ends, unless the screen showed our text is not there — writing a CR is not that evidence, and treating it as such let a leftover be appended to the next input and submitted as one line. **Measured, and it was the dangerous way** (2.1.238, pty): Ctrl+U does **not** leave claude's `!` shell mode — it clears the text and leaves the `!`, so the box looks empty (the disappearance check passes) while still being in shell mode, and the next plain input is submitted as a **shell command** (`command not found: tcq3hello`). One Backspace (0x7F) after the Ctrl+U removes the prefix, and the input after that goes in as an ordinary message; extra Backspaces on an empty box do nothing. So the clear is the two-byte sequence `claudeClearInputKey`, Ctrl+U **then** Backspace — the order matters, because on a box that still holds text Backspace would only take its last character. Only `!` was measured; `/` and `#` are one character too and should be covered by the same sequence, but that is inference, not measurement. The end-of-delivery cleanup lives in **one place**, `submitClaudeInputs` (multiple branches end in failure — session check between inputs, retries exhausted — and a cleanup outside it reaches only one of them). The accepted cost is that a draft the user starts during delivery is erased; the alternative is our `!` line sitting in the box for their Enter
- Don't use the "tty input queue is empty" signal (`FIONREAD`=0) in place of the reflection check — it only means `read()` happened, not that the input box drew it; claude discarded input during initialization, we sent an empty CR onto it and recorded "delivered" (verified empirically). That is why, on Warp, Accessibility permission is a hard requirement for buttons that schedule claude input (command execution doesn't need it). Queue occupancy is good for exactly two things: **backpressure** when writing in chunks, and the **negative** signal "not read yet." **Never infer whose the remaining bytes are** — `FIONREAD` is an unattributed total; it cannot separate ours from keys the user just typed. That is why the branch that compared against the previous sample, judged "didn't grow → ours," and discarded via `tcflush` was removed (the first sample had nothing to compare against so it filtered nothing, and a `10 → 9` — the user typing while claude reads — shrinks the total into the same misjudgment). The cost is a wider window in which our unread bytes linger as residue in the shell's line buffer, but **visible residue beats silent deletion**
- `extension/defaults.js` is the single source for defaults, presets, visibility rules, page classification, and storage keys — the content script, service worker, and options page all load this file first. Page classification is where divergence is most likely: an extension-icon click doesn't go through the content script, so the service worker classifies on its own; if they disagree, commands run on non-repository paths (`/settings/profile`, 404). The options-page CSS tokens mirror the app's `Theme.swift` palette — change a color on one side and change the other too
- The extension trims only ordinary spaces around `claude_inputs`; `trim()` once erased control bytes before the app could reject them, making `["\t"]` disappear and `["\t!echo x"]` change before execution
- On the options page, storage writes happen only through the single [Save] button — import doesn't write to storage either, nor does applying a migration; both only fill the edit state
- Saved commands are snapshots of the presets, so improving a preset never reaches anyone who already pressed Save. The stored `version` (`SETTINGS_VERSION` in `defaults.js`, registry in `extension/migrations.js`) records the generation the settings were **reviewed against**, not rewritten to, and it may move only as the result of an explicit act — applying, applying part, declining, or Reset. Stamping it on every save is the one change that would quietly destroy the feature: the notice clears and the stale commands stay forever. A fresh profile and a legacy one both lack the key; only "is anything else stored" tells them apart. Rewrites are offered for an old preset matched verbatim or a customized command whose *first clause* is exactly the old one — anything looser needs shell parsing and gets listed instead
- Two rules keep that machinery honest, and both were learned by getting them wrong: **the plan is computed over the edit state, never over what storage holds** (an import may cover only some keys, leaving the rest stale and unreviewed; the edit state is what Save will write), and candidates are named by a **runtime uid we mint** rather than an index or anything the data supplied (buttons get typed over and reordered between planning and applying; `adoptButton` mints, `reshapeButton` preserves, `toStoredButton` strips — a uid found in stored data is discarded, because adopting one produced a numeric id the DOM could not match and unchecking an item stopped working). **The version is the generation of the content being written, and nothing is written on top of settings that moved since the load**: a save re-reads every owned key immediately beforehand and *refuses* if anything differs — `storage.sync` has no compare-and-set, and merging would be a guess about whose intent to keep. Guarding the version separately was tried and was worse than nothing: a "highest ever seen" floor stamped a v1 marker onto v0 commands and erased another device's migration in silence. Nothing may be saved before the first load answers, and a load answer from an overtaken request is discarded. Anything read from settings — a command, a repo name, a message action — is a key that may name a prototype member, so look it up in a `Map` or behind `Object.hasOwn`
- Issue buttons attach to the status-badge (Open/Closed) row — placed inside the title (h1) they get pushed to the next line depending on title length, and module CSS class names carry build hashes so they can't be used as selectors (hence finding the flex ancestor wrapping the badge and appending there)
- When verifying drag reordering via browser automation, CDP synthetic input reproduces only `dragstart` through `dragend` and cannot complete a native `drop` (verified empirically) — verify post-drop logic with a synthetic `DragEvent`
- A redraw invalidates every index an in-flight drag captured, so `renderButtons` cancels the drag; a bounds check on `moveItem` is not a substitute, because a same-length replacement leaves the source index valid and moves a row the user never picked up (measured). Both drags share one state and one render, so the cancellation closes the card path too; the card path had the same defect before the row path was added.
- The base directory (`Core/BaseDirectory.swift`) belongs to the app and never to the extension — an absolute path is machine-specific while extension settings ride `storage.sync` across an account, so syncing one would point the other machine at a folder that isn't there. It crosses into Core as a raw string and nothing more: validation, `~` expansion, and clause assembly all happen there, which is what keeps logic out of the untested App target. With it unset the render must stay byte-identical to `z {repo}` — that equivalence is why `{cd}` is assembled by the app rather than the presets carrying a path variable, which would fail every button of an unconfigured user with `Variable {basedir} not provided`
- `{cd}` is the one variable whose value is shell syntax, and therefore the one value exempt from the character whitelist. The exemption is earned, not assumed: `repoEntryCommand` re-runs `sanitizeValue` on every ingredient at the assembly site, and the name is absent from `allowedVariables` so a request carrying it is rejected — check that name **before** assembling, or the reported reason becomes "repo not provided" and hides the collision. Never let request-supplied text into this class. Grouping is `{ …; }`; `( … )` is a subshell and the `cd` wouldn't stick. Measured: a cold zoxide DB exits 1 and a missing `z` exits 127, so one `||` covers both, and `git clone` creates leading directories, so the clone clause needs no `mkdir -p`
- The base-directory clause enters `<base>/<repo>` only after `git -C … rev-parse --git-dir` says it is a repository. A plain `cd` returning 0 answers "does this directory exist", not "is the repository here", and the difference is the whole chain: with an empty `<base>/<repo>` the unguarded form skips the clone and leaves `git fetch`/`git checkout` running in that folder (measured). The `>/dev/null` there is **stdout only** — stderr must stay, because `fatal: not a git repository` and `cannot change to` are what explain the fallback on screen. A directory that is a *different* repository under the right name still passes: that is the same class as `z`'s fuzzy jump and the user's own layout to keep, and remote-URL identity checking is heavy and brittle — revisit if the chain ever gains a destructive step or the base directory stops coming from the user's own typing
- **Foundation re-encodes both `Process.arguments` and `Process.environment` to NFD on Darwin** (measured). Text we hold as NFC — what a user types, and every Swift literal here — arrives at the child decomposed, and Swift's `==` compares by canonical equivalence, so **every assertion that is not on bytes passes either way**. That is why a user's Korean/Japanese/Chinese message to claude used to reach iTerm2 in a form they did not type, and why a `!` input carrying one reached the *shell* that way (a byte-literal tool like `grep` then silently stops matching). The fix is never to normalize — composing to NFC rewrites the bytes of someone who typed NFD just as surely — but to pick a carrier that preserves them: **pipes, file contents, unix sockets and JSON decoding all do; argv and the environment do not**. So **every AppleScript run goes through the one function `runAppleScript` (stdin)**, enforced by a test that walks `app/Sources/**` counting `"/usr/bin/osascript"` occurrences — add a second call site and it fails. Where argv is the only carrier left (the WezTerm no-mux fallback), make the argument **ASCII** instead (`bashANSICQuoted`); an already-ASCII argument cannot be changed by the re-encoding. Paths survive only because APFS resolves both forms to the same node, which is not a property of the value
- **Judge a test toggle by exit status, never by grepping output.** Run from a script, `node --test` and `swift test` emit a different reporter than the interactive one, so a TAP/`# fail` grep matches nothing and reads as success. And a toggle that catches nothing means either the fix is pointless **or the filter missed** — the two look identical, so assert the executed-test count as well
- Test-design decisions and the typed source-audit boundary live in `docs/context/testing.md`
- AppKit layout tests must let AppKit drive layout: forcing `layoutSubtreeIfNeeded()` can continue the traversal after reentrant `setContentSize` and hide the stale clip (`win=702` / `clip=547` in the real cycle versus `clip=702` under forced traversal); one forced call kept six setup-window cases green while the shipped window was visibly broken (#34). Use one shared `settle` helper that pumps the main run loop to a fixed point and fails at a named bound, never a time-only exit, and never force layout from it. A timing investigation may use a disposable single-file AppKit app (`swift foo.swift` with `NSApplication.run()`) to cut variables one at a time, but that replica is not a committed gate because it can drift from the real window; the XCTest run-loop harness reaches the same defect. The setup window applies its size on the next main-queue turn, so code that reads its size synchronously after construction sees the placeholder. Do not close `NSWindow` instances created in tests: `isReleasedWhenClosed` defaults to true, so XCTest's autorelease-pool pop can release the same object again and stop the suite with SIGSEGV; the same code outside XCTest does not reproduce it
- Tool checking (`Core/ToolChecker.swift`) must launch a login shell interactively (`-i`) — `z` is a shell function zoxide defines in rc files, undiscoverable by executable lookup, and a GUI app's PATH/SHELL differ from the login shell's. What "missing `z`" *means* depends on the base directory (`toolIsCritical`): without one it breaks every button, with one the fallback covers it
- GUI apps get a PATH on the order of `/usr/bin:/bin`, so the wezterm CLI must be searched at explicit candidates like `/opt/homebrew/bin`
- New tabs are created in the window the user was looking at — without `--window-id`, `wezterm cli spawn` picks the window from `WEZTERM_PANE`, which a GUI app doesn't have, so the tab lands in the mux's first (= oldest) window (verified empirically). The fallbacks for "no window found" and "the chosen window closed in the meantime" are part of the same unit (`Core/TerminalRunner.swift`) — give up midway and the `wezterm start` fallback opens a new window, resurrecting the very symptom being fixed. iTerm2's `current window` is already the most recently active window and needs no such handling
- The extension ID is pinned by the manifest `key` — the ID must be identical across machines so `storage.sync` settings sync between Chromes on the same account. The private key (`~/Library/Application Support/TerminalCheckout/extension-key.pem`) lives outside the repo; unpacked loading needs only the manifest's public key. The path-based old ID also registered in `allowed_origins` is transitional
- Reflecting extension changes requires a refresh at chrome://extensions — except that **changes that alter the ID (like adding a key) require remove-and-reload, not a refresh**
- When moving to the Chrome Web Store, add the store ID to `Installer.allowedExtensionIDs`. A CWS upload zip cannot contain the manifest `key` field — uploading a key-less zip first to reserve the store ID is the official procedure
